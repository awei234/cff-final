# 论文修改后同步更新注意事项

## 一、修改原则

- 论文修改应在当前工作副本中进行，不直接修改冻结提交包。
- 最终论文以 `paper/paper.pdf` 为准。
- 如果有 `paper.tex`，应以它作为可编辑源文件；如果没有，不要把 PDF 反向重建结果误认为原始源文件。
- 不得新增没有证据支持的数据、实验结果、引用或结论。

## 二、每次修改后必须同步

无论修改内容大小，都要重新确认并更新：

```text
paper/paper.pdf
submission_manifest.json
CHECKSUMS.sha256
```

同时核对：

- PDF 是否可读；
- 页数是否符合要求；
- 文件大小是否正确；
- SHA-256 是否与 manifest 一致；
- `verify_submission.py --stage final` 是否通过。

## 三、修改论文内容时

如果修改涉及摘要、方法、实验、Claim、引用或结论，需要进一步同步：

```text
evidence/research_matrix_authorized/
claim_ledger.json
review.json
retrieval.json
generation.log
```

并重新运行：

1. Claim–Evidence 一致性检查；
2. 引用验证 Rail；
3. 结果一致性 Rail；
4. PDF 编译和最终校验。

论文中的每个重要数字和结论，都应能追溯到对应的实验结果、来源或证据记录。

## 四、只修改排版或措辞时

如果只是修改标题、拼写、段落表达或排版，通常不需要重新生成实验记录，但仍需：

- 重新生成 `paper.pdf`；
- 更新论文页数和 SHA-256；
- 更新 `submission_manifest.json`；
- 重新生成 `CHECKSUMS.sha256`；
- 执行最终校验。

如果页数、生成时间或资源消耗发生变化，还要更新：

```text
resource_report.md
```

## 五、资源和过程记录

以下记录必须基于真实数据，不得补造：

- 模型名称和 Provider；
- 输入、输出及缓存 Token；
- 调用次数；
- 总耗时、单次耗时和重试；
- 检索来源与调用记录；
- 生成日志。

无法确认的字段应写为 `null`、`not_recorded` 或 `imported_not_generated`，不能写成估计的实际账单或精准调用日志。

日志和报告中不得包含 API Key、Access Token、Authorization Header 或其他敏感凭据。

## 六、顺序

1. 完成论文修改并人工确认内容；
2. 重新生成或替换 `paper/paper.pdf`；
3. 运行引用、结果一致性和 PDF 状态检查；
4. 更新 `resource_report.md`（如有变化）；
5. 更新 `submission_manifest.json`；
6. 重新生成 `CHECKSUMS.sha256`；
7. 执行 `verify_submission.py --stage final`；

## 七、不会因论文修改而改变的文件

除非用户明确要求，否则论文修改不应改变：

- `AgenticReviewer/paperReview-AccessToken.txt`；
- 服务器源码快照；
- 已冻结的历史提交包；
- 与本次论文修改无关的第五轮开发改动。

## 八、最终验收标准

论文修改完成后，至少确认：

- PDF 内容与论文描述一致；
- PDF 与 manifest 中的页数、大小和 SHA-256 一致；
- 所有引用和关键 Claim 均有可追溯证据；
- 资源报告与实际记录口径一致；
- 正式提交包最终校验通过；
- 提交包中不包含临时文件、API Key、Token 或本地运行日志。
