# JiuwenSwarm 下一步优先改进清单

## 总体判断

当前项目已经具备“可审计科研半流程 Agent 原型”的基本形态，但下一阶段的重点不应是继续增加主题或入口，而应优先提升真实实验可信度、跨环境复现能力和证据链一致性。

以下五项按优先级排序。

## 1. 修复路径解析与跨环境复现问题

### 当前问题

现有测试仍有路径相关失败：

- v4 服务器工作区：85 passed，3 failed；
- v4 本机工作副本：86 passed，2 failed。

失败集中在项目根目录发现和默认路径解析。当前代码对目录层级和固定路径存在假设，放入完整归档结构后容易指向错误目录。

### 改进内容

- 统一“比赛提交包”和“服务器实验工作区”的项目根定义；
- 从任意工作目录启动时都能正确运行；
- 使用 `sys.executable`，避免依赖机器上的固定 Python 路径；
- 去除用户名、服务器绝对路径和临时目录依赖；
- 修复 `test_paths.py`、`test_cli.py` 中的失败用例；
- 增加 Windows 与 Linux 的最小复现说明。

### 验收标准

```text
pytest -q
```

在项目目录外启动入口也应成功：

```text
python path/to/main.py paths
```

目标：所有路径测试通过，且不依赖当前工作目录。

## 2. 先完成一个真实主题的 Agent 实验闭环

### 当前问题

当前三主题实验主要使用 UCR fixture 基准，实验标签为 `process_evidence_only`。它能证明证据护栏和审计流程可以运行，但不能证明上下文工程、记忆引擎或自我进化确实提升了真实任务效果。

### 改进内容

先只选择 `context-engineering`，建立一个完整、可重复的真实任务：

```text
真实 Agent 任务
→ baseline / prompt-only / full-rail
→ 多个固定 seed
→ 统一任务指标
→ 统计比较
→ Claim—Evidence 绑定
→ 报告与人工确认
```

建议任务是：让 Agent 根据固定资料完成事实检索、工具调用和带证据的回答。

### 对照组

- `baseline`：普通提示词，不提供结构化上下文；
- `prompt-only`：提供任务规范和输出格式，但不启用证据护栏；
- `full-rail`：启用 Claim—Evidence 校验，缺少证据的结论被拦截。

### 建议指标

- 任务成功率；
- 答案准确率；
- 证据覆盖率；
- 无证据结论率；
- 误引用率；
- 平均执行耗时和调用成本。

### 验收标准

- 至少使用 3 个固定 seed，例如 `42、43、44`；
- 三个对照组使用相同输入和任务预算；
- 每个指标都有明确计算公式；
- 结果可以从原始执行记录复核；
- 报告明确区分真实任务结果和流程控制结果。

## 3. 统一 LaTeX 与 PDF 的编译状态

### 当前问题

当前流程能够生成 `paper.tex`，但源码中的生成阶段并不负责实际执行 XeLaTeX；另一方面，提交包验证器又要求状态为 `compiled_verified`。这会导致“声明已编译”和“实际只生成源文件”之间的语义不一致。

### 改进内容

明确区分以下状态：

- `tex_generated`：已生成 LaTeX 源文件；
- `pdf_compile_started`：已开始编译；
- `compiled_verified`：编译成功且通过 PDF 检查；
- `compile_failed`：编译失败。

实际编译时保存：

- 编译命令；
- 编译日志；
- 返回码；
- PDF SHA-256；
- PDF 文本抽取结果；
- 关键章节和引用检查结果。

### 验收标准

- 没有真实编译成功时，不得写入 `compiled_verified`；
- PDF 必须由当前 `paper.tex` 生成；
- 编译失败不得生成伪成功报告；
- 解压后的提交包能够独立复核 PDF 状态。

## 4. 提升检索质量并增加人工来源确认

### 当前问题

当前检索主要依赖标题和摘要的关键词命中，再按相关性分数截取候选资料。这个机制能完成资料收集，但不能充分证明来源真的适合支持研究问题。

### 改进内容

- 记录每次 query、时间和响应哈希；
- 增加标题、摘要、年份、来源类型等维度的评分；
- 合并 DOI、标题和版本重复项；
- 过滤明显无关来源；
- 保存人工批准或拒绝记录；
- 只有 `citation_allowed=true` 的来源才能进入正式论文引用；
- 报告中显示每条引用对应的来源和批准状态。

### 验收标准

每个主题至少保留 5 条人工确认的相关来源，每条来源都具备：

- 查询词；
- 来源 URL；
- 获取时间；
- 内容哈希；
- 相关性理由；
- 人工审核状态。

## 5. 让 Claim—Evidence 账本成为报告的唯一事实来源

### 当前问题

当前已有 `claim_ledger.json`，但验证重点仍偏向于检查 ID 和 JSON Pointer 是否存在，尚不能充分证明每个结论在语义上被实验或来源支持。

### 改进内容

每条结论统一保存：

```json
{
  "claim_id": "C-001",
  "status": "supported",
  "evidence": [
    {
      "artifact": "experiment_results.json",
      "json_pointer": "/arms/2/decisions/0",
      "sha256": "..."
    }
  ]
}
```

建立以下规则：

- 报告只能引用账本中的 claim；
- 没有 evidence 的 claim 不能写成已证实结论；
- 未批准来源不能进入正式引用；
- PDF 中的关键结论必须能够反查到 JSON Pointer；
- 修改实验结果后，相关 claim 的哈希必须失效并重新验证。

### 验收标准

- 每条实验结论至少有一个可验证的 evidence ref；
- 每条正式引用都能追溯到已批准来源；
- 任意篡改实验 JSON 后，验证器能够失败；
- 报告中的 unsupported claims 与账本状态完全一致。

## 推荐执行顺序

```text
1. 修复路径与测试失败
2. 完成 context-engineering 真实实验
3. 统一 PDF 编译状态
4. 提升检索与来源审核
5. 强化 Claim—Evidence 账本
6. 再扩展 memory-engine 和 self-evolution
```

## 暂时不建议优先做的事情

- 增加更多研究主题；
- 增加更多模型 Provider；
- 继续扩展 CLI 入口；
- 只优化论文措辞和排版；
- 批量生成更多 fixture 演示。

当前最关键的问题不是“功能数量不够”，而是“已有功能能否证明真实有效、可复现、可审计”。
