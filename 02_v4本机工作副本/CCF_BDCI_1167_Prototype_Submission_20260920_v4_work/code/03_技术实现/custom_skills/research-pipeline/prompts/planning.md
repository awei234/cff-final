# Planning 实验规划操作手册

> 如何基于研究提案设计严谨的实验计划。改编自 FARS 附录 B Experiment Plan Guidelines。
> **先读 proposal.md 和 idea.json** —— 你的计划必须测试那里描述的声明和假设。
> 执法者：F02 rail 会强制校验 plan.json（baselines≥2、ablation 前置、seeds≥3、budget 估算、datasets 独立声明），不达标会被打回。

## 计划格式

保存为 `plan.json`，结构如下：

```json
{
  "title": "论文标题",
  "hypothesis": "要测试的可证伪假设",
  "reproducibility": {"environment": "Python 3.12 + jiuwenswarm 0.2.4b4", "dependencies": "...", "randomness": "固定 seed"},
  "experiments": [
    {
      "id": "exp1",
      "type": "comparison | ablation | scaling | analysis | systems",
      "title": "简短描述性标题",
      "description": "这一步做什么、为什么",
      "baselines": ["baseline 名称（简单）", "baseline 名称（强/新近）"],
      "seeds": [42, 43, 44],
      "dataset": "数据集名（独立声明，禁止一个数据集当多个用）",
      "metrics": ["标准指标"],
      "budget": {"estimated_minutes": 120, "parallel": true}
    }
  ]
}
```

## 实验设计原则

### 提出可测声明
- 把你的假设表述为可测试的声明
- 设计**可能失败**的实验——如果不能产生负结果，就没有信息量
- 定义什么会**证伪**你的声明

### 选对实验类型

| 声明类型 | 实验类型 | 测量什么 |
|---|---|---|
| "我们的方法优于 X" | 经验对比 | 共享基准上的指标 |
| "组件 A 至关重要" | 消融研究 | 有/无 A 的性能 |
| "这个扩展性更好" | 扩展实验 | 性能 vs 数据/算力/参数 |
| "我们的理论预测 X" | 理论验证 | 已知真值的合成设置 |
| "这个性质成立" | 分析/探针 | 对现有模型/数据的测量 |
| "这个更快/更便宜" | 系统实验 | 延迟、吞吐、内存、FLOPs |
| "这个基准更好" | 基准评估 | 新基准上的已有方法 |

### 谨慎选指标
- 用你任务的标准指标
- 报告**全部**标准指标，不只你赢的那个
- 同时考虑性能和成本（FLOPs、延迟、内存）

### 选能测试你声明的数据集
- 尽可能用标准基准
- 声称鲁棒性 → 测分布偏移数据
- 声称泛化 → 测多个数据集
- 记录：数据来源、规模、划分、预处理

### 公平选 baseline
- **至少 2 个有意义的 baseline**（1 个简单 + 1 个强/新近）
- 所有 baseline 用同等投入跑（同样的算力、同样的调参）
- 绝不与故意削弱的 baseline 对比

### 规划消融
- 每个新组件都计划移除它并测影响
- **跑实验前**就规划消融，不许看完结果再补

### 考虑混淆变量
- 提升是否来自更多参数/数据/算力？
- 对比是否公平（同样的预处理、划分、算力预算）？
- 用已发表 baseline 时，设置是否真正可比？

### 严谨评估
- 用固定随机种子保证可复现
- **方法和所有 baseline 用同一批种子**（公平对比）
- 避免数据泄漏（预处理统计只用训练集等）
- 测试集只用一次做最终评估，不做模型选择

### 常见坑（避免）
- 不在测试集上调超参
- 不与不同预处理/划分的 baseline 对比
- 不只报你赢的指标
- 不声称 SOTA 却不对比真实 SOTA 方法
- 不忽略负结果——如实报告
- 不用单一训练/测试划分
- 不假设深度学习总是更好——测试更简单的替代方案

## 可行性与时长估算

定稿前估算是否匹配资源预算：

1. **估算每个实验的时长**：一次训练/评估/API 调用要多久？用已发表基准或按模型大小和数据集大小的粗略估计。
2. **数独立实验数**：多少 baseline、种子、消融、数据集？哪些能并行？
3. **除以可用并行度**：K 块 GPU、N 个独立 GPU 实验 → 并行时长 ≈ N/K × 单实验时长。CPU 任务按可用核数除。
4. **对比预算**：若估算并行时长超过时间预算，**先**简化计划（少种子、小模型、少数据集）——执行中不许砍。

示例：
- 5 baseline + 1 方法 + 3 消融 = 9 个实验
- 每个 ~30 分钟用 1 块 GPU
- 8 块 GPU：9/8 ≈ 2 批 × 30 分钟 = ~1 小时
- 预算 8 小时 → 有充足余量做可视化和分析

## 计划质量检查清单

- [ ] 每个实验有 id、type、title、description、steps
- [ ] 步骤详细到无歧义可执行
- [ ] 明确的数据集、指标、超参数
- [ ] 至少 2 个有意义的 baseline
- [ ] 每个新组件规划了消融
- [ ] 固定随机种子（同一批种子用于所有方法）
- [ ] 成功标准明确
- [ ] 时长估算匹配资源预算（考虑并行）
- [ ] 计划考虑了所有可用 GPU 和 CPU
- [ ] 包含论文图表的可视化步骤
